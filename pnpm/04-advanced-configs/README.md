# 🛠️ 章节四：pnpm 高级配置与故障排查

恭喜你走到教程的最后一章！
在这一章中，我们将进入前端架构师的视角，看看在实际企业研发生产、历史项目迁移、磁盘空间维护中，有哪些不可不知的 `pnpm` 高级配置与运维神技。

---

## 🩹 1. 历史项目的“解毒剂”：`shamefully-hoist`

### 💥 面临的痛点
当你尝试把一个现有的、用 `npm` 或 `yarn` 维护的历史老项目迁移到 `pnpm` 时，往往会遇到漫天的运行期报错：`Cannot find module 'xxxx'`。
**原因**：这些老项目里充斥着大量的**幽灵依赖**（即代码里 `import` 了没有写在 `package.json` 里的间接包）。
如果要把所有的幽灵依赖一个一个排查并补写到 `package.json` 中，在大型项目里可能会耗费数天甚至数周的时间，极大阻碍了技术升级。

### 💊 pnpm 的救赎：`shamefully-hoist`（羞耻提升）
为了让历史项目能够平滑地、零成本地迁移到 pnpm，pnpm 在 `.npmrc`（npm 配置文件）里提供了一个开关：

1. 在你的项目根目录下创建（或修改）`.npmrc` 文件：
   ```ini
   shamefully-hoist=true
   ```
2. 重新运行 `pnpm install`。

**它的原理：**
它会打破 pnpm 严密的防线，强制把所有的间接依赖包都**平铺并提升（Hoist）**到 `node_modules` 的根目录下，行为变得和传统的 `npm` 极其相似。

> **⚠️ 架构师警告：** 
> 这是一个折中和妥协的方案。它虽然能让老项目瞬间复活，但它同时也重新带回了“幽灵依赖”的隐患。
> **最佳实践：** 在新项目、新架构中，**严禁**开启该配置，保持 pnpm 默认的严谨拓扑；仅在迁移老项目遇到阻力时作为临时过渡工具。

## 🚚 2. 从 npm / yarn 极速迁移：`pnpm import`

如果你的老项目里已经有了一个很健康的 `package-lock.json`（npm）或 `yarn.lock`（yarn）文件，你想在转到 pnpm 时，**百分之百保留原先锁定的版本号**：

不需要删掉 lock 文件重新装，直接在项目根目录下输入：
```bash
pnpm import
```
**原理：**
pnpm 会智能读取现有的 `package-lock.json` 或 `yarn.lock` 里的版本依赖树，并将其零误差地翻译转换成 `pnpm-lock.yaml` 文件。这不仅节省了分析依赖版本的时间，更能确保迁移后线上部署的绝对安全！

## 🧹 3. 磁盘空间的“大扫除”：Store 维护

### 🔍 命令 1：查看全局缓存路径
pnpm 的所有物理包都下载在同一个全局共享的 `Content-addressable Store` 里。如果你很好奇这个 Store 究竟躺在你电脑的什么位置，可以运行：
```bash
pnpm store path
```
你会看到诸如 `C:\Users\<YourName>\.pnpm-store\v3` 或类似的物理路径。

### 🧼 命令 2：一键清理无用缓存 (超好用 🚀)
随着时间的推移，你可能会做很多尝试，创建并删除了许多临时项目。
当一个项目被你整个丢进垃圾桶时，那个项目所引用的物理包可能还在全局 Store 里，但此时已经没有任何项目硬链接指向它们了。这些包就变成了**孤儿包（Orphaned Packages）**。

虽然它们不会影响任何运行，但它们白白占用了你珍贵的磁盘空间。
你可以随时在终端运行：
```bash
pnpm store prune
```
**它的作用：**
pnpm 会扫描全局 Store，检测出所有“未被任何当前项目引用”的包文件，并将它们从磁盘上彻底抹去。
对于经常开发各种前端项目、电脑磁盘吃紧的开发者来说，这个命令能瞬间帮你**腾出几个 GB 甚至几十个 GB** 的空间，堪称磁盘大扫除神器！

## 🔒 4. 依赖安全性：`pnpm audit`

在企业级部署中，安全审计是必不可少的环节。pnpm 提供了开箱即用的漏洞检查：
```bash
pnpm audit
```
它会扫描你项目中所有的依赖（包括间接依赖），并在终端列出所有已知的安全漏洞（CVE 漏洞库），提示你哪些包需要进行 `pnpm update` 升级，护航企业代码安全。
